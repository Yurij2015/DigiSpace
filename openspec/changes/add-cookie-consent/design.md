## Context

`resources/views/layouts/main.blade.php` currently emits Meta Pixel, Google gtag and reCAPTCHA in `<head>`/top of `<body>`, and Plerdy + Microsoft Clarity later in `<body>`, all as inline `<script>` tags that run unconditionally on every request. `public/js/site.js` is a plain vanilla-JS file (no build step, loaded last via `asset('js/site.js')`) that already owns small interactive behaviors (language switcher, keyboard menu handling) using `document.addEventListener`. `public/css/site.css` holds hand-written `.site-*` component styles for that JS (e.g. `.site-language-control__*`). Locale strings live in `lang/{en,uk,pl}/site.php` and are consumed via `__('site.key')` in Blade. `/privacy-policy` renders CMS content from a `Page` row (`FooterPagesController::privacyPolicy`) edited through the existing legacy admin, not through code. See proposal.md - Why/What Changes for motivation and scope.

The three supported locales (en/uk/pl) all get the same opt-in flow rather than a geo/locale-conditional one: GDPR (Art. 3(2)) already applies to the `/pl` locale's visitors regardless of the business's location, and Ukraine's own pending draft law No. 8153 (Art. 17) moves the same direction, so a single uniform mechanism satisfies both without adding locale-branching complexity to consent logic itself.

## Goals / Non-Goals

**Goals:**
- Prevent GA, Meta Pixel, Clarity and Plerdy from executing (no network request, no cookie) until the matching consent category is granted.
- Keep the mechanism plain JS/CSS/Blade, consistent with the existing public-site stack (no new build tooling, no new PHP dependency).
- Make the banner and settings control locale-aware using the existing `__('site.*')` dictionary pattern.

**Non-Goals:**
- Server-side consent logging/audit trail (a database table). The user confirmed cookie/localStorage-only persistence is sufficient for this site's scale.
- A generic, pluggable "add any new tracker" config system. The four known trackers are handled explicitly; adding a fifth later is a follow-up, not blocked by this design.
- Rewriting the trackers themselves (IDs, endpoints) - only how/when they load changes.

## Decisions

- **Gate scripts by deferring their injection, not by conditionally rendering `<script>` tags server-side.** Move each tracker's snippet into a JS function (`loadAnalytics()`, `loadMarketing()`) registered with a small consent-manager module, instead of leaving them as literal inline `<script>` tags in Blade. The consent manager calls the right loader(s) once a category is granted (on first grant, and again on future page loads if already granted). Alternative considered: server-render the scripts only when a `consent` cookie already shows acceptance - rejected because the first visit (the common case needing gating) always has to render blocked, and mixing server-side and client-side gating logic for the same four scripts adds complexity without benefit over doing it entirely client-side.
- **Google Analytics uses Google Consent Mode v2 instead of pure script-load gating.** Emit the `gtag('consent', 'default', {analytics_storage: 'denied', ad_storage: 'denied', ...})` call before the gtag library loads (Google's documented pattern), and call `gtag('consent', 'update', {analytics_storage: 'granted', ...})` from the Analytics loader once granted. The gtag library tag itself can still be deferred until first grant to avoid an unnecessary request when a visitor rejects Analytics outright, but once Analytics has ever been granted on a given page load, use Consent Mode's update signal rather than re-injecting the tag on every load. Rationale: Google explicitly documents Consent Mode as the supported way to reconcile consent state with GA4/Google Ads measurement (avoids GA4 silently modeling/estimating denied traffic in ways that surprise site owners, and avoids the tag being reloaded from scratch on every navigation within an SPA-like flow). Meta Pixel, Clarity and Plerdy have no equivalent first-party consent signaling API, so they keep the simpler "don't inject until granted" approach from the decision above.
- **New `public/js/consent.js`, loaded first in `<body>`, before any tracker snippet.** Keeps the same no-build-step convention as `site.js`. It owns: reading/writing the consent cookie, showing/hiding the banner markup, and exposing `window.DigiConsent.on(category, callback)` so each tracker snippet (still emitted by Blade, just wrapped) registers its own loader instead of running immediately.
- **One first-party cookie, e.g. `digi_consent`, JSON-encoded `{necessary:true, analytics:bool, marketing:bool, ts:number}`.** Read by `consent.js` only (client-side); the server does not need to read it for this change, since 404/robots/SEO behavior is unaffected. A single cookie (not per-category) keeps the "did we already decide" check trivial and matches the user's chosen cookie/localStorage persistence.
- **Banner markup is a Blade partial (`resources/views/components/cookie-consent.blade.php`) rendered once in `layouts/main.blade.php`, hidden by default via CSS, shown by `consent.js` when no decision cookie exists.** Reuses the existing "plain Blade component + site.css classes" pattern (like `site-language-control`) rather than introducing a JS templating approach.
- **"Cookie settings" link lives in the footer bottom bar** (`footer-bottom-bar-content.blade.php`, next to the existing Privacy Policy / FAQ / Support links) as a `<button>` that calls `window.DigiConsent.open()`. Consistent placement with the other legal/meta links visitors already expect there.
- **Privacy policy content update is a data change through the existing admin UI (TinyMCE-edited `Page` row for slug `privacy-policy`), not a code/migration change.** The `Page`/widget CMS model already supports this; adding a migration or seeder would fight the existing content model documented in `docs/content-model.md`.

## Risks / Trade-offs

- [Cookie-only persistence has no server-side audit trail] → Acceptable for this site's scale per user decision; if a future compliance audit needs proof of consent history, that is a separate, explicitly scoped follow-up (e.g. logging decisions to a table), not silently added here.
- [Visitors with JavaScript disabled never see the banner and never get analytics/marketing scripts either] → Consistent with "no consent, no non-essential script": trackers simply never load for that visitor, which is compliant (fail closed).
- [Existing inline tracker snippets must be refactored without breaking their own IDs/config] → Mitigate by keeping each tracker's existing snippet body verbatim inside its loader function; only the invocation is deferred, not the snippet content.
- [Banner must not block Core Web Vitals / layout] → Render it visually hidden (`display:none`) until `consent.js` decides to show it, and keep its CSS minimal, matching the lightweight `site.css` component style already used for the language switcher.
- [Google Consent Mode's `consent('default', ...)` call must run before the gtag library, or Google may not honor it] → Emit the default-denied consent call as the very first inline script in `<head>`, ahead of the deferred gtag tag injection, so the ordering constraint documented by Google is met even though the gtag library itself is not injected until Analytics is granted.

## Migration Plan

No database migration. Deploy is a normal Blade/JS/CSS release: `layouts/main.blade.php`, new `public/js/consent.js`, `public/css/site.css` additions, footer partial change, and locale dictionary additions. The `/privacy-policy` content update is made once through the admin panel after deploy, not part of the code release. Rollback is a plain revert of the commit; no data migration to undo. Run Pint and the existing PHPUnit suite (particularly `PublicSeoTest`, `LocalizedChromeTest`) before handoff to confirm the layout change does not regress metadata or localized chrome.
